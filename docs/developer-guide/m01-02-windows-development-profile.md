# M01-02 Windows development profile

**Status: Framework effective only after separately authorized integration; it does not authorize publication or execution.** This profile applies the [development work profile](development-profile-amendment.md) and requires an explicit work order, documented maintainer acceptance of identified risks and separate authorization of each execution-triggering push. Source: desktop commit `37109e0bc5e02c9c363ada3dd8b508816caa5bbf`, tree `b3f95073fa21689510bdc5d6401d119af73b1bdd`. The failed WO33 attempt and its exhausted one-shot budget are historical evidence; this profile neither reactivates nor consumes that budget.

## Scope and budget

Under an approved work order, use a separate `feature/m01-02-windows-development` branch rooted in the desktop source. Scope repairs to the approved desktop code and this build workflow. Protect requirements, mandatory test definitions, evidence, security controls, lockfiles and source policies: changing those requires the applicable separate authorization and independent review. The workflow fixes the two reviewed lock blobs; dependency or lockfile changes require a newly reviewed profile/workflow revision and explicit authorization.

Allow at most **three cumulative execution attempts, including provisioning**, with a **30-minute job timeout each** and **zero additional cost** once the profile and concrete work are authorized. An attempt is charged before a push can start a job, including startup or provisioning failure. The coordinator maintains one durable ledger across branches, commits, sessions, and specialists, records each authorized candidate and event, and reconciles uncertain outcomes before another attempt. Never assume a counter resets. No automatic reruns, retries, paid or self-hosted fallback. A blocked or ambiguous attempt is not free.

Use only a fresh regular disposable GitHub-hosted Windows x64 runner, subject to a preflight showing public-repository usage and actual zero additional cost. No personal data, repository or environment secrets, write-capable token, artifact transfer, installer, desktop EXE execution, or release. Confirm actual token permissions and configured triggers before each authorized push. Only approved official dependency sources and ordinary GitHub runner operations are in scope; stop on observed unapproved destinations or uncertain external effects. Ordinary official-registry HTTPS redirects are not independently attested.

The workflow may provision only locked Rust crates and npm packages from approved official registries, with normal TLS and integrity checks, no npm lifecycle scripts, and a fresh private process-scoped cache. Rust build scripts and other dependency code can execute during the build. The runner has temporary service credentials and no verified inner process, filesystem or network isolation: dependency code can access runner resources, make external requests, alter files or logs, and cause effects not completely monitored. A disposable runner and read-only repository token do not eliminate these risks. The maintainer must explicitly review and accept the actual scope and residual risks before execution.

## Trigger and attempt sequence

A feature-only workflow cannot be assumed dispatchable using GitHub `workflow_dispatch`: the workflow must exist on the default branch. The draft instead uses a push restricted to the development branch. Push creates a real run, so before each attempt: verify actual public repository, cost, permissions, all applicable push triggers and candidate SHA; verify an authorized budget slot; record the decision and consume the slot; then explicitly authorize only that candidate and push. The workflow checks event, branch, checkout SHA, desktop ancestry, reviewed lock blobs and tool versions. External controls, not the workflow, bind each push to authorization and enforce the total budget. No concurrent attempts. The first candidate is based on the desktop source; subsequent authorized fixes may add commits on this branch without resetting the ledger.

After an ordinary deterministic build error, preserve logs and record the failed candidate, exit code and remaining budget. Diagnose and repair only within approved paths and scope; routine corrections need no individual new work order or repeated independent review unless they affect protected security boundaries or mandatory evidence, and required final candidate review remains mandatory. Record the new SHA and repeat preflight before a further specifically authorized push within the same budget. Do not relax controls or change protected evidence to make a build pass. Stop on a security-critical deviation, unapproved source, unexpected token rights, unclear side effects or unknown budget; reconcile and obtain the necessary decision before proceeding. A fresh attempt is never automatic.

## Outputs and later startup

The workflow checks the expected EXE, frontend index, Tauri permission, ACL and capability files. These are preliminary, potentially manipulable existence observations. Successful compilation does not show that a GUI starts, renders or that the bridge works.

A separate work order and approval should select an isolated, disposable interactive Windows x64 VM with a controlled display session and appropriate WebView2 runtime, synthetic data, no personal or repository secrets and no write-capable token. Specify artifact provenance and transfer authorization, rollback, exposure and cost before starting the app. Observe rendering and the intended bridge calls separately; neither the headless build nor this proposal authorizes execution on a personal host or artifact transfer.

## Controls and limits

The former one-shot diagnostic's exact sole-parent/three-file candidate restriction and full before/after file inventory are not repeated: ordinary approved repair commits require different candidates, and a disposable development build records each candidate and checks the tracked tree and index instead. The manual external ledger replaces the one-attempt-only organizational budget; each individual run still rejects reruns. Lock blob identity retains the previously reviewed registry, integrity and bounded bundled-package contents, rather than reparsing those immutable locks on every attempt. Mandatory security and quality evidence, independent review and human decisions are not waived. These controls do not protect against a compromised process falsifying its own logs or Git metadata.
